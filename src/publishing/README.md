# Channel publications

Each event has one HTML text message or one caption-bearing media publication with a ten-dot interest bar above the Russian headline, summary and source links. The reviewer returns only actual issues in a remarks array, or an empty array when there are none. Only non-empty remarks appear as `Заметки проверяющего: <причина>`. Existing sent snapshots are not refreshed merely to change review wording. Review is informational, not an admission gate. The verdict and reason come from the generation JSON and are retained in the publication snapshot. New sends still require the minimum score and current generation.

Follow-ups show the full topic headline, `Новое`, `Ранее было опубликовано`, `Первоисточники`, `Вторичные источники` and `Предыдущие публикации`. Sources combine the whole thread; previous-post links are oldest first. Repetitions add sources to the latest sent post instead of sending again. Snapshots hold at most 90 sources, dropping inherited secondary links first.

Source links come from current collected mentions, source-only reports and successfully read, relevant research documents. All eligible current mention origins remain in the full stored source list; the writer's partial URL selection cannot hide them. A single origin classification distinguishes primary publications from relays. Collected links classified as origins stay in the primary source list even when a crawler cannot read them; that is provenance, not independent verification. There is no claim-level citation or source-authority contract. Public feed/website reads still require collector metadata. Expired, superseded, irrelevant, inaccessible or failed fetched pages are not published as sources. Primary research sources appear first. Titles come from read content, not advertising anchors.

The text-post renderer respects Telegram's 4096 visible UTF-16 and 100-entity limits. It compacts source labels, then trims earlier history before new details without dropping links or reviewer notes. Stored snapshots retain full text and labels. Media captions show at most three compact source links, not the full stored list. There are no buttons or pages; edits clear old inline keyboards.

New media publications use one caption-bearing request, never a text message followed by replies. Native JPEG/PNG images and MP4 videos take priority; at most ten total items go into one compatible album. If no native items exist, one document-only group carries the original formats. A single item uses `sendPhoto`, `sendVideo` or `sendDocument`. Unselected items are omitted, not sent later. Uploads keep the original bytes.

The caption fits Telegram's 1024 decoded UTF-16 units. It keeps the headline, score, core details and up to three compact source links, with bounded review notes and earlier context. The full immutable snapshot retains all text and sources. The first caption-bearing media message is canonical. Album edits use `editMessageCaption` with the same bounded renderer; text publications still use `editMessageText` and the 4096-unit renderer.

The durable `delivery_kind` distinguishes text from album publications. Existing text-plus-reply publications and pending attachment retries retain their legacy lifecycle. They are never retroactively converted or resent as albums. Their legacy `sendMedia` batches remain separate from new album delivery.

Before a Telegram send is authorized, a durable plan freezes the selected items and stores their temporary bytes. The admission transaction claims that exact plan with the send attempt. Success commits the canonical ID, every item ID, the batch outcome and publication status together. Confirmed uploads erase their temporary bytes immediately. Maintenance also erases all remaining bytea within seven days of the original download, including unpublished and unknown sends. Hashes, outcomes and Telegram IDs remain for review and authorized deletion.

Known rate-limit rejections can resume the frozen plan after their saved cooldown. Permanent failures do not retry. Interrupted or ambiguous sends require reconciliation or manual review and are never resent blindly. Reconciliation checks the original caption/link fingerprint and attempt window, then requires the whole Telegram media group, its expected count and first caption message. A matching caption alone cannot complete an album. Unknown caption edits reconcile against the bounded caption fingerprint rather than the full text rendering. Authorized deletion removes tracked siblings before the canonical caption, records per-item progress, and refuses unknown upload outcomes. A reviewed deletion rejected with 429 can resume only under the same unexpired approval after rechecking its snapshot, content hash and story version. Unknown deletion outcomes remain for manual review.

Duplicate reports stage a source-only snapshot using the sent headline, details, earlier summary, score and review unchanged. Source-only edits do not require regenerating the published text. A successful edit switches the published snapshot pointer; unknown edits retain the old pointer for reconciliation. Current input, settings, destination, bot ownership and saved cooldowns are checked before delivery. Admission denials are diagnostic records, not Telegram attempts. Explicit repairs use their existing approval path.

`publishDigest` captures eligible ready events in one query. The default `digestCron` is `0 */3 * * *`. Events arriving during selection wait for the next digest. Manual-origin ownership still prevents an automatic path around a manual run's cap.

`startPublicationMaintenance` resumes previously prepared sends, reconciliation, edits and replacement deletions every five seconds by default. It does not select new ready events. `PUBLICATION_READY_INTERVAL_MS` accepts 1000 to 60000 milliseconds. See [timing and ownership](../../docs/immediate-publishing.md).

`previewPublicationRepair` inspects tracked posts without writes. `repairExistingPublications` edits tracked canonical posts before deleting authorized duplicates. Unknown or untracked messages are not deletion targets. `{ includeVerificationTest: true }` includes only the registered technical test. No Telegram callback polling runs.
